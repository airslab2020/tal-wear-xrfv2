# Data preprocessing and temporal conventions

There are two entry points: prepare the published synchronized datasets for TAL, or reconstruct the earlier raw-source processing. Using published features/annotations is the shortest route to reproduce the paper protocol.

## WEAR: use the official processed release

Required files for the paper settings:

```text
WEAR/
  annotations/30fps/wear_split_1.json ... wear_split_18.json
  raw/inertial/25hz/sbj_0.csv ... sbj_17.csv
  processed/combined_features/30fps/60_frames_30_stride/sbj_0.npy ... sbj_17.npy
```

The 18-fold protocol uses the 18 processed TAL subject IDs. This should not be conflated with the total number of people in the original collection.

Each CSV has a subject-ID column, 12 acceleration columns, and the label column. Each combined NPY has shape `[T,2648]` and stores `[IMU600; RGB1024; Flow1024]`. The 600-D IMU part is flattened as channel-major `[12,50]`. The adapters restore `[50,12]` before the TinyHAR encoder.

The actual configurations use 25 Hz inertial labels/samples, 50-sample windows, 30 fps annotations, 60-frame visual descriptors, and stride 30 frames. Thus the descriptor/window length is 2 seconds, with 1-second temporal steps. The different rates serve different purposes; do not change `sampling_rate: 25` to 50 merely because `imu_window_size: 50`.

If only the separate IMU and I3D features are available:

```bash
python tools/prepare_wear.py \
  --imu-dir /path/to/WEAR/raw/inertial/25hz \
  --i3d-dir /path/to/WEAR/processed/i3d_features/30fps/60_frames_30_stride \
  --annotation-dir /path/to/WEAR/annotations/30fps \
  --output-root data/wear
```

The assembler uses 50 samples and stride 25, keeping the strict final-window condition of the upstream sliding-window routine. It crops IMU windows to the supplied I3D row count, checks the 2048-D RGB+Flow layout, and copies the official annotation JSONs byte-for-byte. It does not normalize sensors or reannotate action boundaries.

For recording/synchronizing new data, the upstream scripts in `data_creation/` cover synchronization-point identification, synchronized sensor streams, raw inertial CSVs, and feature/annotation assembly. Their original tutorial is [data_creation/README.md](../data_creation/README.md). These manual-collection examples require their recording metadata and are not replacements for the paper's official 30 fps/25 Hz files. The original tutorial's 60 fps/50 Hz example is a different setting.

RGB/Flow I3D descriptors should be obtained from the official processed release or its feature-extraction workflow. This code release does not add an optical-flow estimator or a new I3D extractor.

## XRF V2: synchronized H5-to-TAL bridge

Input layout:

```text
XRFv2-release/
  data/
    imu_50hz_853_video_aligned.h5
    video_feature_853_video_aligned.h5
  annotations/tal_annotations_video_aligned/
    activitynet_tal_853.json
    label_map.json
```

The H5 paths are:

- `/samples/<sample_name>/imu`: `[N,5,6]`;
- `/samples/<sample_name>/video_feature`: `[T,1024]`.

Sample names have the form `<volunteer>_<scene>_<sequence>`. The bridge intersects the annotation/IMU/video sample sets, crops to the shortest whole-second duration, clips action intervals to this duration, and writes:

```text
data/xrfv2_plus/
  processed/combined_features/imu_flatten_video_1hz/sbj_*.npy
  raw/labels_1hz/sbj_*.csv
  annotations/loso/xrfv2_plus_loso_s00.json ... xrfv2_plus_loso_s15.json
  id_map.json
  prepare_summary.json
```

Refer to the actual output filenames printed/generated by the bridge for additional manifests. In the synthetic unit test there are two volunteers, so the bridge generates two rather than sixteen folds.

```bash
python tools/prepare_xrfv2_plus_actionformer.py \
  --release-root /path/to/XRFv2-release \
  --output-root data/xrfv2_plus
```

The combined layout is `[T,2524]`: 1500 flattened IMU values followed by 1024 visual values. The stored IMU order is `[device,channel,time]`; the adapter restores `[time,device×channel]`. Devices are left wrist, right wrist, left phone, right phone, and glasses; the selected six channels are acceleration XYZ and angular-velocity XYZ.

LOSO is by **volunteer**, not by `sbj_*` recording index. All recordings from the held-out volunteer use the `Validation` subset; all other volunteers use `Training`. The original 16-volunteer manifest and sample IDs must be retained.

## XRF V2: raw-source construction scripts

The original processing scripts were also collected under `preprocessing/xrfv2/`. Their file paths now default to `./data/xrfv2_source`, and can be set with:

```bash
export XRFV2_SOURCE_ROOT=/path/to/raw-source-workspace
```

| Script | Input | Output / purpose |
| --- | --- | --- |
| split_imu_by_device_and_command.py | `imu/`, `command_time/` | Device-separated and command-window-separated IMU files and manifests |
| resample_imu_per_second_50hz.py | `imu_command_time_split_manifest.csv` and source text files | Exactly 50 interpolated samples per second, per-device files and quality manifests |
| build_imu_50hz_853_h5.py | Resampled files, `wifi_853_names.txt`, `wifi_time_dims.csv` | Canonical 853-recording IMU H5, using the historical reference-length manifest |
| monitor_extract_kinect_rgb_features.py | Cropped videos, command JSONs, target sample list, duration overrides | Command-aligned, per-second 1024-D Swin3D-B feature arrays |
| build_video_feature_853_h5_remote.py | Feature arrays and `kinect_rgb_feature_monitor/video_h5_sample_order_853.txt` | Canonically ordered video feature H5 |
| trim_modalities_for_video_alignment.py | IMU H5 and `kinect_rgb_feature_monitor/duration_overrides.json` | Video-aligned IMU H5; use `--modalities imu` |
| build_tal_annotations_video_aligned.py | `command_time_video_aligned/` and video-feature H5 | TAL annotations, label map, and split metadata |
| extract_features.py | `video_cropped/` | Earlier whole-video feature extraction example; not the command-aligned release entry point |

The `wifi_*` manifest names refer to the historical canonical sequence set and lengths; WiFi features are not used by the IMU–visual model. These raw-source metadata files and videos belong to the dataset construction workspace and are not bundled with this code repository.

Example RGB extraction, after preparing the cropped-video workspace and metadata:

```bash
python -m pip install -r requirements-preprocessing.txt
# Install ffmpeg/ffprobe through your platform's package manager.
CUDA_VISIBLE_DEVICES=0 python preprocessing/xrfv2/monitor_extract_kinect_rgb_features.py \
  --target-list "$XRFV2_SOURCE_ROOT/kinect_rgb_feature_monitor/wifi_853_names.txt" \
  --video-root "$XRFV2_SOURCE_ROOT/kinect_action_cropped_tracks" \
  --command-dir "$XRFV2_SOURCE_ROOT/command_time" \
  --feature-root "$XRFV2_SOURCE_ROOT/kinect_rgb_secondwise_feature" \
  --extract-ready --device cuda --batch-size 2
```

The extractor uses torchvision Swin3D-B with `KINETICS400_IMAGENET22K_V1` weights, 15 sampled RGB frames per second, and an identity classification head. Pretrained weights are downloaded through torchvision; they are not part of this Git repository.

Raw-source scripts regenerate their designated output files/directories. Run them in a dataset-construction workspace, and keep the original downloaded release separately. For TAL reproduction, prefer the synchronized H5 bridge above.
